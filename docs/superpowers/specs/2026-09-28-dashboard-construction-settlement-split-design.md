# 대시보드 실적 — 시공 실적 / 정산 분리 (설계)

- 작성일: 2026-09-28
- 상태: 설계 확정, 구현 계획 작성 전
- 티어: A (회계 정합성 · 두 레포 API 계약 · 타임존)
- 선행 작업: PR #41 공무 페이지 ERP 주간 실적 (`2026-09-28-gongmu-erp-weekly-actuals-design.md`)

## 1. 배경

사장님 요구: 주간 보고서의 담당자별 실적 월 합계 = 대시보드 실적.

이 회사의 금액 기록은 두 축으로 나뉜다.
- **시공**: 공무가 한 공사의 진행분을 금액으로 환산한 것. ERP `공사이력.성과금액`.
- **정산**: 그 공사에 대해 실제로 계산서를 끊은 금액. 기성(`기성.기성액_공급가`)과 준공(새로 끊은 금액).

두 축은 더하는 관계가 아니다. 대부분의 정산은 이미 시공으로 잡힌 일에 대한 청구다.

### 지금 대시보드 도넛의 문제
지금 도넛의 실적은 `monthly-kpi.ts`의 `monthlyRevenue`이다.
```
monthlyRevenue = 그 달 공사이력 성과금액 + 그 달 준공 건의 (준공액 − 공사이력 전 기간 누계)
```
그런데 도넛의 분모인 **월간 목표는 시공분만으로 잡힌다**(사용자 확인, 2026-09-28).
분자에는 준공 보정이 들어가고 분모에는 들어가지 않아서, 기준이 어긋난 %를 보여주고 있었다(2026-07-08 달성률 127.19% 사고와 같은 구조).

2026-09-28 운영 DB 실측 (천원, 읽기 전용):

| 월 | 시공 | 준공 보정 | 지금 도넛 실적 | 보정 ÷ 시공 |
|---|---|---|---|---|
| 7월 | 211,319 | 152,321 | 363,640 | 72% |
| 8월 | 472,265 | 49,434 | 521,699 | 10% |
| 9월 | 232,431 | 61,385 | 293,816 | 26% |

준공이 몰린 달일수록 도넛이 시공 진도와 무관하게 부풀었다. 7월에는 72%였다.

### ERP 내부의 '성과'는 틀리지 않았다
매출손익 페이지, 홈 월별 차트, 홈 KPI "이번 달 성과"는 같은 `시공 + 준공 보정`을 "성과"라고 부른다.
이 숫자는 공사 하나의 성과를 전 기간 합치면 준공액과 같아지도록 만든 **매출 인식 축**이다. 매출손익에서는 이 정의가 맞다.
어긋난 곳은 이 숫자를 **시공 목표의 분자로 쓴 대시보드 도넛 하나**뿐이다. 그래서 ERP 내부는 바꾸지 않는다.

결과적으로 ERP 홈 "이번 달 성과"(9월 293,816)와 대시보드 "시공 실적"(9월 232,432)은 다른 숫자가 된다.
라벨이 다르고, 서로 다른 축을 가리킨다. 사장님이 두 화면을 비교하고 ERP 쪽도 나누자고 하시면 별도 작업으로 한다.

## 2. 결정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 도넛 %와 큰 숫자 | **시공 실적 ÷ 목표** | 목표가 시공분만이므로 분자와 분모의 기준을 맞춘다. %가 내려가는 것은 감수한다. 지금까지 보여준 값이 틀렸던 것이다 |
| 정산 표시 | 캡션에 별도 줄 + 클릭하면 상세 팝업 | 정산에는 환수(음수)가 섞여서, 숫자만 보여주면 "왜 이것밖에 안 되지?"를 화면에서 확인할 수 없다 |
| 정산 — 기성 | 그 달 `기성일`의 `기성액_공급가` | 계산서 한 장이 곧 한 행이다 |
| 정산 — 준공 | 그 달 `준공일` 건의 **금회지불액 = 준공액_공급가 − 그 공사의 기성 전 기간 누계** | `준공액_공급가`에는 언제나 총액이 저장된다(2026-07-29 확정). 총액을 넣으면 앞서 끊은 기성을 두 번 센다. 주간 보고서에도 새로 끊은 금액을 적는다(사용자 확인). `OrderForm.tsx`의 `금회지불액`과 같은 정의다 |
| 환수(금회지불액 < 0) | 0으로 깎지 않고 그대로 합산하고, 빨갛게 표시 | 돈이 실제로 반대로 흐른 것이다 |
| 반올림 | 시공은 **공사이력 행마다** 천원으로 반올림한 뒤 공사별로 합친다. 정산은 계산서 행마다 반올림 | 공무 페이지(`gongmu/_lib/erp-실적.ts`)와 같은 규칙이다. 두 화면을 나란히 놓고 볼 때 1천원이라도 다르면 틀린 표다 |
| ERP 내부 성과 화면 | 변경 없음 | §1 참조 |
| API | 기존 칸은 그대로 두고 `split` 칸을 추가 | §3 참조 |

### '준공 보정'과 '준공 정산'은 다른 숫자다
- 준공 보정 = 준공액 − **공사이력(시공) 누계**. 매출 인식 축에서 중복을 빼기 위한 값이다.
- 준공 정산(금회지불액) = 준공액 − **기성 누계**. 새로 끊은 계산서 금액이다.

9월에는 우연히 61,385와 62,208로 비슷하게 나왔지만, 차감하는 기준이 다르다. 코드에서 둘을 섞으면 안 된다.

## 3. API 계약 (프로듀서 = yjs_erp, 소비자 = yjs_Dashboard)

`GET /api/kpi/monthly-performance`의 응답에 `split`을 **추가**한다. 기존 칸(`amounts`, `formatted`, `breakdown`, `period`, `label`, `updatedAt`)의 값과 의미는 한 글자도 바꾸지 않는다.

```jsonc
"split": {
  "construction": {
    "rows": [{ "지중no": "...", "공사명": "...", "금액천원": 12345, "일자": [1, 2], "야간일자": [2] }],
    "totalThousand": 232432
  },
  "settlement": {
    "rows": [{ "지중no": "...", "공사명": "...", "구분": "기성 2차" /* 또는 "준공" */, "일": 23, "금액천원": -1234 }],
    "totalThousand": 220453
  }
}
```

- `totalThousand`는 `rows`의 합이다. 따로 계산하지 않는다.
- 금액이 0천원인 행은 뺀다. 합계는 바뀌지 않는다.
- 정렬: 금액 큰 순, 같으면 지중no 순. 조회할 때마다 순서가 흔들리지 않게 하기 위해서다.
- `split`의 달은 기존 칸과 **같은 `getMonthlyPeriod(now)`, 같은 `now`**로 정한다.

### 검토 후 기각한 방식
- `breakdown`의 의미를 "시공만"으로 바꾸기: 같은 이름의 칸이 말없이 다른 뜻이 된다. 옛 대시보드가 에러 없이 틀린 제목을 계속 달고 있게 된다.
- 새 엔드포인트(`/v2`): Bearer 문지기와 설정 URL이 두 벌이 된다. 칸 몇 개를 추가하는 일에 비해 과하다.

### 옛 응답에 대한 소비자 동작
`split.construction`을 쓸 수 없으면(옛 ERP, 행 누락, 합계 불일치) **`monthlyRevenue`로 대신 채우지 않는다.**
그 값은 틀렸다고 확인한 정의이고, 화면에서는 티가 나지 않는다.
대신 ERP 조회 실패와 같은 경로(저장된 대체값으로 도넛을 그리고, 팝업에 "불러오지 못했습니다")로 처리한다.

| 파일 | 변경 |

### `monthly-split.ts`
- `build월시공내역(공사이력전체, 수주목록, 투입실적, from, to)`
  - `[from, to)`의 공사이력(`준공정산=false`는 `load성과재료`가 이미 걸러 준다)을 행마다 `Math.round(원/1000) || 0`으로 바꾼 뒤 공사별로 합친다.
  - 일자와 야간일자는 `build월성과내역`과 같은 방식이다(야간은 투입실적의 수주_id + 같은 날로 빌려온다).
- `build월정산내역(기성전체, 수주목록, from, to)`
  - 기성: `기성일`이 `[from, to)` 안인 행마다 한 줄. 구분은 `기성 {차수}차`(차수가 없으면 `기성`)이다.
  - 준공: `준공여부 && 준공일 ∈ [from, to) && 준공액_공급가 != null`인 수주마다 한 줄. 금액 = 준공액 − 그 수주의 **기성 전 기간 누계**.
  - 기성누계는 `기성일`이 비어 있는 행까지 포함해 **전 기간**으로 만든다. 월 목록에서는 `기성일`이 빈 행이 빠진다(귀속시킬 달이 없다).
- `getMonthlySplit(supabase, now, 성과재료Promise, 투입실적)`
  - 기성 전 행을 `fetchAllRows`로 받는다(현재 226행, 1000행에서 조용히 잘리는 것을 막는다).
  - 투입실적은 `getMonthlyKpiData`가 이미 읽은 그 달 행을 재사용할 수 있으면 재사용한다. 구현 계획에서 경로를 정한다.

날짜는 전부 `'YYYY-MM-DD'` 문자열로 비교한다. `new Date()`로 날짜를 읽지 않는다. 오늘의 달은 `partsKST()`를 쓰는 `getMonthlyPeriod`가 정한다.

### `_normalize_split`
- 섹션(`construction`, `settlement`)마다 `_normalize_breakdown`과 같은 방어를 한다. 행이 하나라도 안 읽히거나, 행 합계와 ERP가 보낸 `totalThousand`가 다르면 **그 섹션만** `None`으로 한다.
- `split`이 없거나 객체가 아니면 `None`.
- 반환하는 키는 영문으로 바꾼다(기존 `breakdown`과 같은 방식): construction 행 `jijungNo, name, amountThousand, days, nightDays` / settlement 행 `jijungNo, name, kind, day, amountThousand`.

### 화면 동작
| 상황 | 도넛 | 캡션 정산 줄 |
|---|---|---|
| construction 있음, settlement 있음 | 시공 ÷ 목표 | "정산 N천원" (클릭하면 팝업) |
| construction 있음, settlement 없음 | 시공 ÷ 목표 | "정산 불러오지 못함" |
| construction 없음 | 기존 ERP 실패 경로(대체값) | 표시하지 않음 |

- 실적 팝업: 제목은 "○월 시공 실적 상세", 행은 construction이다. 합계 줄 문구는 "도넛의 '실적'과 같은 값"을 유지한다.
- 정산 팝업: 열은 `지중No / 공사명 / 구분 / 일 / 금액(천원)`. 음수는 기존 `minus` 스타일. 합계 줄은 "캡션의 '정산'과 같은 값". 0건이면 "○월에 끊은 계산서가 아직 없습니다"로 표시하고, 불러오기 실패 문구와 구분한다.
- 문자열은 전부 `escapeHtml`을 거친다. 숫자는 normalize 단계에서 숫자로 고정한다.
- 정산 줄의 "최신화" 시각은 기존 캡션과 같은 `updatedAt`을 쓴다(같은 응답이다).

## 6. 검증

### ERP (vitest, `monthly-split.test.ts`)
- 시공 반올림: 499원 행 2개 → 공사 합계 0천원(행마다 반올림). 원 합계를 먼저 반올림하는 방식과 결과가 다른 사례를 넣는다.
- 준공 금회지불액이 기성 **전 기간** 누계로 차감되는지: 5월 기성 + 9월 준공.
- 기성이 없는 준공 → 금액 = 준공액.
- 환수: 기성누계 > 준공액 → 음수 행이 남고 합계에 반영된다.
- `기성일`이 null인 기성: 월 목록에는 없고 준공 차감에는 포함된다.
- 달 경계: 말일 행은 포함, 다음 달 1일 행은 제외.
- `준공액_공급가` null인 준공 → 행 없음.

### Dashboard (pytest, `test_erp_kpi_split.py`)
- `split` 없음 → `None`.
- construction 합계 불일치 → construction `None`, settlement는 유지.
- 정상 응답 → 키 변환과 숫자 강제.

### 실측 대조
- 로컬 ERP로 9월 응답을 받아 `split.construction.totalThousand`가 공무 페이지 9월 달력 기준 **232,432**와 같은지 확인한다.
- `split.settlement.totalThousand`가 설계 실측값 220,453(기성 158,245 + 준공 62,208, 원 단위 합산 후 반올림 기준)과 행 반올림 오차 범위 안에서 맞는지 확인한다.
- 기존 `amounts.monthlyRevenue`와 `breakdown`이 변경 전과 같은지 확인한다.

### 브라우저
- 로컬 대시보드를 로컬 ERP에 붙여 도넛, 캡션, 팝업 두 개를 확인한다.
- ERP 응답에서 `split`을 뺀 상태로 한 번 띄워, 대체값 경로와 "불러오지 못했습니다" 문구를 확인한다.

## 7. 배포

- 순서: **ERP 먼저 → 대시보드 나중.** 반대 순서면 새 대시보드가 옛 ERP를 받아 대체값을 보여주는 시간이 생긴다.
- 대시보드 배포 직후 사장님께 한 줄 공지: "도넛이 시공 실적 기준으로 바뀌어 %가 내려갑니다(9월 기준 약 21% 낮아짐). 정산(기성·준공 계산서)은 아래 줄에 따로 표시됩니다."
- 운영 DB 변경 없음(읽기만).

## 8. 범위 밖
- ERP 내부 성과 화면(매출손익, 홈 차트, 홈 KPI)
- `기성일`이 빈 과거 기성 200행(2026-06 이관분, 7월 이후 생성분 중에는 0건). 과거 월 정산을 보여주는 기능이 생기면 그때 다룬다
- 담당자별 정산 집계(9월 준공 건 대부분이 담당 미지정)
- 기존 `breakdown` 칸 삭제: 대시보드가 `split`으로 완전히 옮겨간 뒤 별도로 진행한다
