# 공무 페이지 — ERP 담당자별 주간 실적 조회 (설계)

- 작성일: 2026-09-28
- 상태: 설계 확정, 구현 계획 작성 전
- 티어: A (회계 정합성 · RLS 쓰기 경로 · 타임존)

## 1. 배경

사장님 요구: 주간 업무 보고서의 담당자별 실적 월 합계 = 대시보드 실적.

9월 4주차 회의록(`9월 4주차_주간공정회의록.xlsx`)을 ERP 운영 DB와 대조한 결과(2026-09-28 실측):

| 담당 | ERP 공사이력 (9/21~) | 회의록 금주 실적 |
|---|---|---|
| 김무선 | 9,687 | 9,687 (일치) |
| 김상훈 | 2,405 | 2,574 |
| 이재규 | 1,419 | 4,260 (ERP 미입력분 포함 추정) |

원인은 구조에 있다. 보고서는 담당자 메모로 먼저 쓰이고 ERP 입력은 나중이라, 둘이 어긋나도 알아챌 장치가 없다.
처방은 **ERP에 입력한 실적이 곧바로 담당자별로 집계되는 조회 화면**을 만들고, 주간 보고서 폴더에 "금주 실적 확인하기" 바로가기를 거는 것이다.
보고서를 쓸 때 이 화면을 참고하는 습관이 생기면 ERP 선입력이 자연히 따라온다.

### 기존 공무 페이지의 상태
- `/gongmu`의 숫자는 수동 입력 테이블 `공무_주간보고.금주실적`에서 온다. 6월 말(2026-W26) 이후 입력이 0건이다.
- `공사이력.담당공무_id`는 실적 행마다 채워지고 있다. 9월 39행 중 17행은 수주의 담당자와 다른 사람이라, 행 단위 기록이 맞다.
- 이력 수정 시트(`progress/_components/이력수정Sheet.tsx`)에 담당공무 칸이 없어서, 잘못 넣거나 빠뜨리면 고칠 방법이 없다.

## 2. 범위

**포함**
- `/gongmu` 메인을 ERP `공사이력` 기반 담당자별 **공사 진행 실적** 조회로 교체
- 미지정 이력 모아보기 + 그 자리에서 담당 지정
- 이력 수정 시트에 담당공무 칸 추가
- `/gongmu` 날짜 판정의 KST 버그 수정

**제외**
- 정산(준공·기성) 담당자별 집계: 9월 준공 23건이 거의 전부 담당 미지정이다. "누가 끊은 계산서냐"를 ERP에 기록하는 업무 규칙이 먼저 필요하다.
- 월간계획·달성률 표시, 목록 복사 버튼, 엑셀 내보내기
- 2026-09 이전 데이터. 과거 보고서를 다시 쓸 일이 없으니 지정할 이유가 없다.
- 대시보드 실적/정산 분리. 별도 작업이며 ERP API에 칸을 추가하는 방식으로 이미 검토했다.

**유지**
- 구 수동 양식 `/gongmu/[id]`는 삭제하지 않는다. 목록 패널 하단 링크로만 연결한다. 열 때만 조회하므로 평소 부하는 0이다.

**결정 근거(사용자):** 메뉴를 하나로 모으는 게 덜 헷갈린다. 이 페이지의 주 용도는 각 공무가 바로가기로 들어와 자기 이번 주 실적을 **조회**하는 것이다.

## 3. 주차 규칙

- 한 주 = 월~일.
- **한 주는 통째로 한 달에 속하고, 소속 월은 그 주 금요일의 달이다.** 보고서는 그 주의 마지막 평일에 작성하기 때문이다.
  - 9/28~10/4 → 10/2 → 10월 1주차
  - 8/31~9/6 → 9/4 → 9월 1주차 (8/31 실적은 9월 보고서에 들어간다)
  - 4/27~5/3 → 5/1 → 5월. ISO 규칙(목요일 기준)이면 4월이 되므로 두 규칙이 갈리는 사례다.
  - 2026-12-28~2027-01-03 → 2027-01-01 → 2027년 1월
- 추석처럼 수요일에 미리 쓰는 주도 소속은 금요일이 정한다.
- 기존 `getWeeksInMonth`(달에 걸친 주를 양쪽 달에 다 넣음)는 이 계산에 쓰지 않는다.
- **금주 = 오늘(KST)이 속한 주.** 기본 화면은 금주가 속한 달이다. 예: 2026-09-28에 열면 10월 1주차.
- 하한 = 2026년 9월 1주차(2026-08-31~). 그보다 이른 `?month`·`?week`는 기본 화면으로 보낸다.

### 타임존
`/gongmu/page.tsx`와 `src/lib/week.ts`는 `new Date()` + `getFullYear/getDate`로 날짜를 읽는다.
ERP 서버 시계는 UTC라서 **월요일 KST 00:00~09:00에는 금주가 지난주로 잡힌다.**
새 코드는 오늘 날짜를 `partsKST()`로만 얻고, 이후 날짜는 `'YYYY-MM-DD'` 문자열 비교와 UTC 기준 날짜 산술로만 다룬다.

## 4. 데이터와 계산

### 읽기 (`/gongmu` 서버 컴포넌트, 세션 클라이언트 + RLS)
1. `공무담당자`: `id, 이름`, id 순
2. `공사이력`: **한 번의 조회**로 두 기간의 합집합을 받는다.
   두 기간은 주 기준 `[첫 주 월요일, 마지막 주 다음 월요일)`과 달력 기준 `[달 1일, 다음 달 1일)`이다.
   9월이면 `[8/31, 10/1)`이다. 주 기준 집계와 달력 기준 비교값을 같은 행 배열에서 걸러 쓰므로 두 숫자의 재료가 같다.
   - `준공정산 = false`
   - 칸: `id, 수주_id, 작업일자, 성과금액, 담당공무_id, 수주(지중no, 공사명)`
   - `fetchAllRows`로 페이지 단위로 받는다(PostgREST 1000행에서 조용히 잘리는 것 방지).

### 계산: `src/app/(dashboard)/gongmu/_lib/erp-실적.ts` (순수 함수, DB 접근 없음)
- `주소속월(월요일)`, `달의주목록(year, month)`, `금주(오늘KST)`
- `build담당자별실적(행, 담당자목록, 선택주)` → 담당자별 `{ 선택주, 월누적, 건수, 행목록 }` + 미지정 묶음 + 삭제된 담당자 묶음
- 달력 기준 차이 계산: 주 기준 합 − 달력 기준 합, 그리고 차이를 만든 날짜 목록

### 원칙
- **모든 합계는 행에서 파생한다.** 카드, 소계, 요약이 같은 행 배열을 더하므로 서로 어긋날 수 없다.
- **단위는 천원.** 행마다 `Math.round(원/1000)`으로 반올림하고, 합계는 반올림된 행의 합이다. 손으로 더한 값과 카드가 달라서는 안 된다.
- 성과금액 `null`은 0으로 계산한다. 음수는 그대로 둔다.
- **검산식:** 담당자 합 + 미지정 + 삭제된 담당자 = 그 주들의 공사 진행 합계
- 이 합계의 정의는 대시보드 '실적'(공사 진행분)과 같고, 기간만 주 기준이다.

## 5. 화면

- **상단:** `공무 · YYYY년 M월`, ◀ ▶ 월 이동(하한에서 ◀ 비활성), 그 달의 주 칩(`1주차 9/28~10/4`, 금주 표시). 주 선택은 `?week=`.
- **요약 카드:** 선택 주 합계, 월 누적 합계, 설명 줄
  > 달력 기준 9월: 232,431천원 · 차이 +1,627천원 = 8/31 실적 포함(9월 주차 소속)

  "대시보드"라고 쓰지 않는다. 대시보드 실적은 아직 준공분까지 합친 값이라 이 숫자와 다르다.

  차이가 0이면 "달력 기준과 같음"으로 표시한다.
- **담당자 카드 그리드:** 등록된 공무담당자 전원을 id 순으로 보여준다. 0도 표시한다. 카드 내용은 이름, 선택 주 실적(강조), 월 누적, 건수.
- **미지정 카드:** 맨 끝에 항상 둔다. 0건이면 "미지정 없음 ✓". 숨기면 "없음"과 "못 불러옴"이 구별되지 않는다.
- **삭제된 담당자 카드:** 해당 행이 있을 때만 "(삭제된 담당자 #id)"로 보여준다.
- **카드 클릭 → Sheet 패널:** 주별 묶음(선택 주가 맨 위), 칸은 날짜·지중no·공사명·금액(천원), 주마다 소계. 하단에 `주간 보고서 직접 작성(구 양식) →` 링크(`/gongmu/[id]`).
- **미지정 패널:** 같은 목록에 행마다 담당 드롭다운과 저장 버튼. 저장에 성공하면 `router.refresh()`.
- **반응형:** 카드는 한 줄에 1장(휴대폰)/2장(태블릿)/4장(PC). 지금 규칙과 같다.
- 제거: 기존 KPI 3칸(월간계획·공무 구분·달성률).

## 6. 쓰기

### 단일 저장 함수: `src/app/(dashboard)/progress/_lib/update-공사이력.ts`
```ts
update공사이력(id: number, patch: Partial<{ 작업일자: string; 성과금액: number | null; 담당공무_id: number | null }>)
  → { ok: true } | { ok: false; reason: 'error' | 'not-updated' }
```
- `.update(patch).eq('id', id).select('id')`로 실제로 바뀐 행을 돌려받는다. **1행이 아니면 실패다.**
  RLS에 막히거나 그 사이 삭제된 행은 에러 없이 "0행 수정"으로 끝난다. 확인하지 않으면 "저장됐습니다"라고 거짓말하게 된다.
- 바꿀 칸만 보낸다(부분 업데이트). 폼 전체를 덮어쓰지 않는다.
- 권한(`is_whitelisted()` 정책)과 변경 기록(`audit_공사이력` 트리거)은 이미 걸려 있어서 마이그레이션이 없다.

### 호출부
- 미지정 패널: `{ 담당공무_id }`
- 이력 수정 시트: `{ 작업일자, 성과금액, 담당공무_id }`. 드롭다운에 "미지정"도 넣어 잘못 지정한 것을 되돌릴 수 있게 한다.
  - `ProgressHistoryTable.tsx`의 조회 select와 `progress/_types.ts`의 `공사이력행`에 `담당공무_id`를 추가한다.
  - 공무담당자 목록을 prop으로 받는다.
  - 같은 시트의 삭제도 `.select('id')`로 0행 확인을 거친다.
- 동시 수정은 나중에 저장한 쪽이 이긴다. audit_log에 남으므로 받아들인다.

## 7. 실패 처리

| 상황 | 동작 |
|---|---|
| 공사이력·담당자 조회 실패 | 카드를 0으로 그리지 않고 "ERP 실적을 불러오지 못했습니다" |
