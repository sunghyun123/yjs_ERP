# 선택 공사 이력 목록 (슬라이스 2) 설계 스펙

> 작성일: 2026-06-29
> 선행: `2026-06-29-progress-percent-write-consistency.md` (슬라이스 1, 동일 브랜치에 커밋됨)

## 배경 / 문제

슬라이스 1에서 입력 폼의 % 입력 기준을 "작업일자 직전 누계"로 자동 반영하도록 배선했다(Task 3). 실사용 피드백:

1. **자동 반영이 직관적이지 않다.** 날짜만 바꿔도 기준값(직전누계)이 화면에 보이지 않고, 사용자가 값을 한 번 입력해야 입력칸에 누적%가 환원되어 "갑자기 값이 바뀐 것처럼" 헷갈린다.
2. **자동 반영을 추가한 원래 이유**는 백필 시 입력/현황 탭을 오가며 %를 직접 계산하는 불편을 없애려던 것. 그런데 **선택한 공사의 이력이 입력 화면 아래에 바로 보이면**, 사용자가 그걸 보고 직접 판단·수정하면 되므로 자동 반영이 불필요해진다 — 오히려 방해가 된다.

반면 현황 탭에서 **행 클릭 → 수정 Sheet의 원/% 토글**로 한 레코드를 원·%로 자유롭게 보는 경험은 좋다는 평가.

## 목표

공사이력 **입력 화면**에서 공사를 선택하면, 그 공사의 이력이 입력 폼 **바로 아래**에 최신순으로 표시되고(10개씩 페이지네이션), 행을 클릭하면 수정/삭제할 수 있다. 입력칸의 "직전 누계 % 자동 반영"은 제거하고, 입력칸 %는 **전체 누계 기준 누적목표 %**(슬라이스 1 이전 동작)로 되돌린다.

### 비목표 (YAGNI)
- 입력 화면 아래 목록에 **기간 필터·공사명 검색**은 넣지 않는다. 그 역할은 현황 탭이 담당한다(역할 분리).
- 서버 측 페이지네이션은 하지 않는다(공사당 이력 수는 적음 — 클라이언트 분할로 충분).

## 아키텍처

증분(원)이 1차 정본이라는 슬라이스 1의 원칙은 유지. 핵심 변경은 **입력 폼의 % 기준 롤백** + **선택 공사 이력의 인라인 표시·수정**이다.

### 컴포넌트

| 컴포넌트 | 종류 | 책임 |
|---|---|---|
| `이력수정Sheet` | **신규(공용 추출)** | 한 레코드 수정 UI: 작업일자 입력 + 원/% 토글 성과 입력 + 저장/삭제. 현황 탭과 입력 폼 목록이 공유. |
| `선택공사이력목록` | **신규(경량)** | 선택 공사의 `이력목록`을 최신순 정렬 → 10개씩 페이지 분할 렌더. 행 클릭 → `이력수정Sheet`. |
| `ProgressInputForm` | 수정 | % 기준 롤백(`직전누계값` 제거), 하단에 `선택공사이력목록` 추가, 수정/삭제 후 `이력목록` 재동기화. |
| `ProgressHistoryTable` | 수정 | 인라인 수정 Sheet 로직을 `이력수정Sheet`로 위임(중복 제거). |
| `_lib/pagination.ts` | **신규** | 페이지 분할 순수함수 + 단위 테스트. |

### `이력수정Sheet` 인터페이스(초안)

```ts
type 이력수정SheetProps = {
  open: boolean
  onOpenChange: (open: boolean) => void
  row: 공사이력행 | null            // 수정 대상(지중no/공사명/수주_id/원자료 포함)
  records: { id: number; 작업일자: string; 성과금액: number | null }[] // 그 공사 전체 이력(직전누계 계산용)
  loading: boolean                  // records lazy-fetch 중 여부
  onSaved: () => void               // 저장 성공 → 호출부가 재조회
  onDeleted: () => void             // 삭제 성공 → 호출부가 재조회
  showToast: (ok: boolean, msg: string) => void
}
```

- base(하도적용금액)와 `edit직전누계`(id 필터 + strict `<`)는 Sheet **내부에서** `row`·`records`·편집 중 `editDate`로 파생한다(슬라이스 1 Task 4 로직 이전).
- `records`가 비어 있으면(불러오기 실패) base에 `null`을 넘겨 `성과Input`이 자동으로 원 모드로 강등된다 — 슬라이스 1과 동일한 안전장치.
- 저장/삭제의 supabase 호출은 Sheet 내부에서 수행하고, 결과만 `onSaved`/`onDeleted`로 알린다. 재조회 주체는 호출부(현황 탭은 `fetchData`, 입력 폼은 `handle공사선택` 재호출 또는 동등 재조회).

### 입력 폼 % 기준 롤백

- `성과Input`에 넘기는 `직전누계={직전누계값}` → `직전누계={누계성과금액}`(전체 총계).
- `직전누계값` useMemo 제거(폼에서 더 이상 사용 안 함).
- `누계성과금액`·`최근작업일자`는 슬라이스 1처럼 `이력목록`에서 `useMemo`로 파생(단일 소스 유지).
- `직전누계` 함수(`percent.ts`)는 **삭제하지 않는다** — `이력수정Sheet`가 계속 사용.

### 의도적 비대칭

- **입력칸 %** = 전체 누계 기준 누적목표(`base`, `누계성과금액`). 신규 입력은 보통 최신 회차라 전체 누계가 자연스럽다.
- **수정 Sheet %** = 그 작업일자 직전 누계 기준(`base`, `edit직전누계`). 과거 특정 날짜 레코드는 "그 시점까지 누적"이 맞다.
- 이 차이는 의도된 것이며, 두 화면의 라벨 문구로 의미를 구분한다.

## 데이터 흐름

```
공사 선택
  └→ handle공사선택: 이력 fetch → 이력목록(state, 단일 소스)
        ├→ 누계성과금액 (useMemo)   → 입력칸 % base 기준 + 우측 패널
        ├→ 최근작업일자 (useMemo)   → "마지막 등록 기록"
        └→ 선택공사이력목록         → 10개씩 페이지 렌더
              └→ 행 클릭 → 이력수정Sheet
                    └→ 저장/삭제 → onSaved/onDeleted
                          └→ 폼이 이력목록 재조회 → 위 파생 전부 갱신
```

## 페이지네이션

- 클라이언트 측. `이력목록`(이미 전체 fetch됨)을 최신순 정렬 후 `pageSize=10`으로 분할.
- 순수함수 `paginate(items, page, pageSize)` → `{ pageItems, totalPages, page }`. 경계(빈 목록, 마지막 페이지 미만 채움, page 범위 초과)를 단위 테스트로 검증.
- 공사 변경 시 page를 1로 리셋.

> 향후 리스크: 이력이 PostgREST 기본 1000행에 근접하는 공사가 생기면 `handle공사선택`의 전체 fetch가 조용히 잘릴 수 있다(기존 백로그 인지 사항). 현재 범위에선 안전, 인지만 한다.

## 에러 처리

- 이력 fetch 실패: 기존 폼 동작 유지(목록 비어 있음 표시), 토스트로 알림.
- 수정 Sheet의 records lazy-fetch 실패: base=null → 원 모드 강등(% 비활성), 토스트 안내.
- 저장/삭제 실패: 토스트로 알리고 Sheet 유지(재시도 가능).

## 테스트

| 대상 | 방식 | 이유 |
|---|---|---|
| `paginate` | 단위 테스트(Vitest) | 분할/경계 로직이 순수함수 — 회귀 방지 |
| `이력수정Sheet` 추출 | 동작 보존 확인(타입/린트/수동) | 리팩터라 동작 불변이 핵심 |
| 입력칸 % 롤백 | 기존 `percent` 테스트 | 환산 함수 자체는 불변 |

수동 확인:
- 공사 선택 → 아래 목록에 최신순 이력, 10개 초과 시 페이지 분할.
- 목록 행 클릭 → 수정 Sheet에서 원/% 토글, 저장/삭제 후 목록·누계 갱신.
- 입력칸 % = 전체 누계 기준(날짜를 바꿔도 자동으로 값이 채워지지 않음 — 자동 반영 제거 확인).
- 현황 탭의 수정 Sheet가 추출 후에도 이전과 동일하게 동작.
