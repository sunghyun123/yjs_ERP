# 성과금액 퍼센트(%) 입력 — 설계 (Design Spec)

- **날짜:** 2026-06-24
- **출처 피드백:** 김도윤 차장 — "공사이력 등록에서 성과를 원단위로만 입력하는 건 비효율적. 규모 큰 공사(예: 20억)는 100만원어치 해도 1%도 안 올라 금액 산정이 무의미하고, 소액 공사는 보통 하루에 끝나 오히려 금액 계산이 더 번거롭다. 원단위·% 두 방식을 병행 지원해야 한다."
- **티어:** A (성과 정합성 = 핵심 도메인 로직)
- **변경 범위:** `src/app/(dashboard)/progress/_components/ProgressInputForm.tsx` 한 곳 + 순수 환산 헬퍼/테스트 신설. **DB 스키마·저장 로직 무변경.**

---

## 1. 목표와 비목표

### 목표
- 공사이력 등록 시 성과를 **원(₩) 또는 % 중 선택**해 입력할 수 있다.
- % 입력은 "이번 작업이 전체 공정의 몇 %인가"(= **증분 Δ%**)를 의미한다.
- 어떤 방식으로 입력하든 **DB에는 항상 `성과금액`(원)만 저장**된다.

### 비목표 (YAGNI)
- DB에 % 컬럼을 추가하지 않는다.
- 매출손익·준공정산·달성률 등 다운스트림 로직을 수정하지 않는다.
- 100% 초과 가드, % 입력 경고 표시는 하지 않는다.

---

## 2. 핵심 원칙 — 단독 소스 불변

[[seonggwa-source-of-truth]]: 공사이력의 `성과금액`(원)이 성과의 **단독 소스**다.
% 입력은 **순수 입력 환산 레이어**일 뿐이며, 저장되는 값은 언제나 원이다. 따라서
매출손익 합산·달성률 계산 등 기존 파생 로직은 입력 방식과 무관하게 정확성을 유지한다.

### 환산식
```
성과금액(원)  = Math.round( 입력% / 100 * 하도적용금액 )   // % → 원 (저장용)
표시%        = 성과금액 / 하도적용금액 * 100              // 원 → % (% 모드 표시·역산용)
```
- `하도적용금액 = 수주금액_공급가 × (1 − 보험료율) × 하도전용율` (기존 폼에 이미 계산되어 있음)

---

## 3. 상태 모델

`성과금액`(원, `number | null`)을 **유일한 정본 상태(canonical)** 로 유지한다.

- `handleSave`와 기존 파생 계산(`delta달성율`, `저장후달성율`, `현재달성율`, `저장후누계`)은 **변경하지 않는다.** 이들은 이미 원 기준이라 입력 방식과 독립적이다.
- 새 상태: `입력모드: '원' | '%'`, 기본값 `'%'`.
- 입력 컴포넌트는 모드를 내부에서 관리하고 **부모에는 항상 원만** `onChange(원)`으로 올린다 → 인터페이스 경계가 깨끗하다(부모는 % 의 존재를 몰라도 됨).

### 모드 전환은 무손실
- % 모드로 전환 시: 현재 정본 원 값을 `표시%`로 역산해 입력칸에 채운다.
- 원 모드로 전환 시: 정본 원 값을 그대로 보여준다.
- **타이핑 중 반올림 떨림 방지:** 기존 `MoneyInput`이 `display` 로컬 state를 두는 패턴과 동일하게, % 입력칸도 로컬 표시 문자열을 둔다. 정본 원 값이 외부 요인(모드 전환, 공사 변경, 저장 후 리셋)으로 바뀔 때만 표시 문자열을 동기화한다.

---

## 4. UI

- 성과금액 라벨 옆에 `[ 원 | % ]` 세그먼트 토글. **기본 %.**
- **% 모드:** 입력칸에 `%` 접미사, 소수점 허용(예: `33.33`). `inputMode="decimal"`.
- **원 모드:** 기존 `MoneyInput` 그대로(천 단위 콤마).
- **환산 결과 표시:** 오른쪽 "Δ공정 달성률" 카드가 이미 `formatKRW(성과금액) ÷ formatKRW(하도적용금액) × 100`을 표시하므로, % 모드에서 입력한 값의 **환산된 원 금액이 그 카드에 그대로 노출**된다. 추가 UI는 최소화한다.

---

## 5. 경계 동작

| 상황 | 동작 |
| --- | --- |
| 하도적용금액 `null` 또는 `0` (수주금액·보험료율·하도전용율 미입력) | % 환산 불가 → **% 토글 비활성화 + 원 모드 강제**. "공사단가 정보가 없어 % 입력 불가" 안내 문구. |
| 저장 후 누계 달성률 100% 초과 | **가드·경고 없음.** 초과 성과(over-performance)·보정 입력이 빈번하므로 원 입력과 동일하게 그대로 허용. |
| 공사 미선택 상태 | 하도적용금액이 없으므로 위 규칙에 따라 원 모드. |
| % 입력이 빈 값/0 | `성과금액 = null`(또는 0) — 기존 원 입력과 동일하게 저장 버튼 비활성 조건 유지. |

---

## 6. 테스트

순수 환산 함수를 분리해 단위 테스트한다(기존 `orders/_lib/completion.test.ts`와 동일 패턴).

- `percentToWon(pct, 하도적용금액)`: 정상 환산, **반올림 경계**(예: 0.5원 → 반올림), `base = 0/null` 시 처리.
- `wonToPercent(won, 하도적용금액)`: 역산, `base = 0/null` 시 처리.
- 라운드트립: 원 → % → 원이 반올림 오차 범위 내에서 보존되는지 (정본은 원이므로 % 표시 떨림이 정본을 훼손하지 않음을 확인).

---

## 7. 구현 체크리스트(요약)

1. 순수 헬퍼 `percentToWon` / `wonToPercent` 작성 + 테스트.
2. 입력 컴포넌트에 `입력모드` 상태 + `[원|%]` 토글 추가.
3. % 모드 입력/표시 로직(로컬 표시 문자열, 소수점, % 접미사).
4. 하도적용금액 없음 → 원 모드 강제 + 토글 비활성 + 안내.
5. `handleSave`·파생 계산 무변경 확인(회귀 방지).
