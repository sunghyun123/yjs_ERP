# 공사이력 쓰기 측 % 일관성 (슬라이스 1) — 설계

날짜: 2026-06-29
상태: 설계 확정 대기

## 배경 / 문제

공사이력의 `성과금액`은 **그 날짜의 증분(원)**을 저장하는 1차 정본이다.
누적 달성률(%)은 저장하지 않고 읽는 순간 파생한다 (`Σ증분 ÷ 하도적용금액 × 100`).
`하도적용금액 = 수주금액_공급가 × (1 − 보험료율) × 하도전용율`.

이 모델 위에서 쓰기 측에 두 가지 통증이 있다.

1. **백필 시 % 기준이 틀림.** 같은 공사를 25·26·28 입력하고 27을 빼먹은 경우, 27을
   % 모드로 등록하려면 "26까지의 누적 %"가 필요하다. 그런데 입력 폼은 % 기준으로
   **전체 누계(`누계성과금액`)**를 쓴다 — 여기엔 28의 증분까지 포함돼 기준이 틀린다.
2. **% 입력자가 수정 시 원 계산을 강요당함.** `ProgressHistoryTable`의 수정 Sheet는
   `성과금액`을 **원 단위로만** 편집한다. % 모드로 입력해 금액 계산을 피하려던 사용자가
   수정할 땐 졸지에 원 금액을 직접 계산해야 한다 — % 모드의 존재 이유가 깨진다.

## 결정된 아키텍처 (상위 맥락)

- **% 는 DB에 저장하지 않는다.** 1차 정본은 증분 원 하나, 누적 %는 읽기 시 한 곳에서 파생.
- 근거: base(수주금액·보험료율·하도전용율)는 거의 안 바뀌고, 바뀌면 과거 %가 새 요율을
  따라가는 게 올바른 동작 → 파생이 이를 공짜로 준다. 저장이면 base 변경 시 전부 재기록 필요.
- 슬라이스 1 = **쓰기 측 % 일관성**(이 문서). 슬라이스 2 = 읽기 측 % 가시성(별도 스펙).

## 목표 / 비목표

목표:
- 백필 시 % 입력 기준을 "그 작업일자 직전까지의 누계"로 정확히 잡는다.
- 수정 Sheet에서도 입력 폼과 동일한 원/% 토글로 편집할 수 있게 한다.
- 위 둘이 공유하는 누적 파생 함수와 입력 컴포넌트를 추출한다 (슬라이스 2의 토대).

비목표:
- 이력 카드에 % 표시 (슬라이스 2).
- 엑셀 추출 / 기성청구 읽기 경로, DB 뷰 (슬라이스 2 이후).
- `<=` 기준 `누계까지` 함수 (슬라이스 2에서 필요할 때).
- 증분 모델 자체 변경 (매출손익이 증분을 월별 합산하므로 불변).

## 설계

### 1. 토대 — `직전누계` 순수함수

`src/app/(dashboard)/progress/_lib/percent.ts`에 추가:

```ts
// 기준일 '직전'까지의 누계 증분(원). strict < 기준일.
// 날짜당 1건(unique 제약)이라 기준일과 같은 날 레코드는 자동 제외된다.
export function 직전누계(
  records: { 작업일자: string; 성과금액: number | null }[],
  기준일: string,
): number
```

`strict <`인 이유 — 두 소비자가 같은 함수를 쓰기 위함:
- **폼 백필:** 27 입력 시 기준일=27, 27 레코드는 아직 없음 → `<27` = 26까지 누계.
- **수정 Sheet:** 날짜 D 레코드 수정 시 자기 자신(D에 위치)은 `<D`에서 제외 → 자기 빼고 직전 누계.

### 2. `성과Input` 공용 추출

현재 `ProgressInputForm.tsx` 내부의 `성과Input` / `PercentInput` / `MoneyInput`을
새 파일 `src/app/(dashboard)/progress/_components/성과Input.tsx`로 이동. 폼·수정 Sheet 공유.
`ProgressHistoryTable`의 중복 `MoneyInput`도 이 공용 파일로 통합 제거.

- 시그니처: `성과Input({ value, onChange, 하도적용금액, 직전누계 })` — `value`는 증분(원) 정본.
- `PercentInput`의 `누계` 파라미터 → **`직전누계`로 개명**(기준이 "총계"가 아니라
  "기준일 직전 누계"임을 명확히). 내부 수학(`증분 = 누적목표원 − 직전누계`)은 불변.
- 모드 기본값 `'%'`, `환산불가`(base 없음)면 `원` 강제 — 폼·수정 공통.

### 3. 폼 상태 모델 (records 단일 소스)

`ProgressInputForm.tsx`:

- **제거:** `누계성과금액`, `최근작업일자` state.
- **추가:** `이력목록: { id, 작업일자, 성과금액 }[]` state.
- **파생(`useMemo`):**
  - `누계성과금액 = Σ 이력목록.성과금액` (총계) — "마지막 등록 기록" 패널 + 저장후누계용.
  - `최근작업일자 = max(작업일자) | null` — 백필해도 max라 덮어쓰기 버그 소멸.
  - `직전누계 = 직전누계(이력목록, 작업일자)` — % 입력 기준으로 `성과Input`에 전달.
- `handle공사선택`: 누계 계산 후 버리던 records를 `set이력목록(records)`로 보존.
- `handleSave`: insert를 `.insert(...).select('id, 작업일자, 성과금액').single()`로 바꿔
  반환행을 `이력목록`에 append → 누계·최근·직전 자동 재파생.

일반(최신 날짜 append) 케이스는 `직전누계 == 총계`라 동작 불변. 백필일 때만 기준이 정확해짐.

### 4. 수정 Sheet 배선

`ProgressHistoryTable.tsx`:

- 메인 쿼리 조인 확장: `수주!수주_id(지중no, 공사명, 수주금액_공급가, 보험료율, 하도전용율)`.
  `_types.ts`의 `공사이력행` 타입 `수주` 모양도 base 원자료 포함하도록 확장.
- `openEdit(row)`: base는 조인값으로 계산. 그 수주의 **전체 이력 lazy-fetch** → `editRecords` state.
  로딩 중엔 `성과Input` 자리에 스피너.
- `직전누계 = useMemo(직전누계(editRecords.filter(r => r.id !== editRow.id), editDate),
  [editRecords, editDate, editRow])` — 자기 제외(strict `<` + id 필터 이중안전), editDate 변경 시 재계산.
- Sheet의 `MoneyInput` → 공용 `성과Input`(원/% 토글)로 교체.
- **DB 쓰기 불변:** `.update({ 작업일자: editDate, 성과금액: editAmount })`. `editAmount`는 여전히
  증분(원). %는 저장 전 원으로 환산될 뿐 — "정본은 원" 원칙 유지.
- records fetch 실패 시: 토스트 + `원` 모드 강등(직전누계 모르면 % 부정확하므로).

### 5. 라벨 구분 (의도적 수용)

백필 시 `성과Input`의 % 필드(그 날짜까지 누적)와 우측 "저장 후 누계"(전체 총계 %)는
서로 다른 숫자를 보인다 — 다른 질문에 답하기 때문. 혼동 방지를 위해 단어로 구분:

- `성과Input` % 모드 라벨: `성과 (이 작업일자까지 누적)`
- 우측 패널 라벨: `저장 후 누계` → `저장 후 전체 누계`

## 테스트

`percent.test.ts`에 `직전누계` 단위 테스트:
- 빈 배열 → 0
- 전부 기준일 이전 → 합
- 섞인 날짜 → `<기준일`만 합산
- 기준일과 같은 날 레코드는 제외 (strict 검증)
- 정렬 안 된 입력에서도 정확

컴포넌트 동작(% 토글, 백필 기준)은 위 순수함수 + 기존 `percentToWon`/`누적목표를증분으로`
테스트로 수학이 보장되며, 배선은 수동 확인.
