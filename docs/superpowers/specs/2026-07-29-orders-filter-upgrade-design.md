# 수주대장 조회 필터 고도화 + 작업구분 입력 — 설계 스펙

- 날짜: 2026-07-29
- 티어: **A** (도메인 조회 로직 · 연도 판정 · 합계 정합성)
- 대상 화면: 수주대장 (`src/app/(dashboard)/orders/`)
- 브랜치: `feat/orders-filter-upgrade`

## 1. 배경 — 받은 피드백

> 사내 전산 시스템(ERP 등)에서 수주 건을 조회할 때 연도별(25년/26년 분리), 발주처별,
> 공사 진행 상태별(진행 전, 진행 중, 완료 등)로 직관적인 필터링 및 조회가 가능하도록
> UI/UX 개선 필요.

여기에 요청자와의 확인으로 두 가지가 덧붙었다.

- "발주처별"은 **원청사별**을 뜻한다. 수주에는 발주자와 원청사가 따로 저장돼 있고, 조회 축은 원청사다.
- 공사구분 필터에 **총가**를 추가한다 (현재 전체/단가/민수 → 전체/총가/단가/민수).

별건으로 함께 처리: 수주 등록 폼 "계약 정보"에 **작업구분** 입력 칸 추가.

## 2. 현재 상태 조사 (2026-07-29, 실 DB 564건)

| 축 | 분포 |
| --- | --- |
| 작업구분 | 저압 330 · 고압 176 · 보수 19 · 미입력 39 |
| 공사구분 | 단가 536 · 민수 16 · 총가 9 · 관급 2 · 미입력 1 |
| 연도(지중no) | 2025년 389 · 2026년 173 · 2024년 1 · 연도미상 1 |
| 원청사 | 13곳. 정우전설 426 + 에스제이이 110 = 전체의 95%, 나머지 11곳은 1~17건, 원청사 없음 1건 |
| 상태(이력건수 기준) | 완료 258 · 진행전 202 · 진행중 104 |
| 상태(`시공상태` 컬럼) | 완료 277 · **NULL 196** · 미시공 47 · 시공중 44 |

조사에서 드러난 사실 세 가지가 설계를 결정했다.

1. **`작업구분` 컬럼은 이미 존재하고 값도 이미 들어있다.** `수주.작업구분 text null`
   (`src/types/database.ts:106`), 이관 스크립트가 엑셀 4번째 열에서 적재
   (`scripts/migrate-수주.ts:48,201`), `수주행` 타입과 `page.tsx:13` 조회에도 이미 포함.
   **폼에서만 노출이 빠진 상태** → 마이그레이션 불필요.
   기존 값(저압/고압/보수)이 신규 선택지와 정확히 일치해 어휘 충돌도 없다.
2. **`시공상태` 컬럼으로 '진행전'을 판정하면 안 된다.** 미시공은 47건뿐인데 실제 이력 0건은
   202건이고, NULL이 196건(35%)이다. 이 컬럼을 쓰면 155건이 진행전에도 진행중에도
   안 걸리는 유령이 된다. (도넛이 이미 이 컬럼을 폐기한 이유 — `_lib/type-status.ts:9`)
3. **거래처 중복 의심 1건**: `에스제이이`(110건)와 `에스제이이2`(1건)가 따로 등록돼 있다.
   이번 범위 밖이지만 필터 드롭다운에 나란히 뜨므로 거래처 정리 백로그로 기록한다.

## 3. 확정된 결정

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 진행전 판정 | **공사이력 0건** (도넛과 동일 규칙) | 세 화면이 같은 정의를 써야 함. `시공상태`는 NULL 35%로 사용 불가 |
| 연도 소스 | `지중no` 정규식 (`연도추출`) | 수주 테이블에 수주일·계약일 컬럼이 없고 착공일은 45% NULL. 지중no는 결측이 사실상 없음(564건 중 1건) |
| 연도 기본값 | **전체** | 수주대장은 '대장 전체'를 보는 화면. 올해로 시작하면 열자마자 389건이 사라진 것처럼 보인다 |
| 원청사 목록 | 수주에 **등장하는 13곳만** + '원청사 없음' | 거래처 전체를 넣으면 결과 0건인 선택지가 생긴다 |
| 원청사 UI | 검색창 있는 드롭다운 (`SearchableSelect` 공용화) | 요청자가 말한 '검색 헬퍼'. 원청사가 늘어도 견딤 |
| 관급 처리 | 필터에서 **민수에 병합** | 회사 내 규정으로 이미 통합. 도넛의 `유형병합`과 같은 규칙 |
| 작업구분 | 필터에는 **넣지 않음**, 폼 입력만 | 요청 범위 유지. 필터는 이미 6개 |
| 필터 바 배치 | 2줄 분리 (조회 축 / 표시 축) | 금액기준은 필터가 아니라 표시 전환. 성격이 다른 두 축이 섞이지 않게 |
| 어휘 | 도넛은 '미진행' 유지, 수주대장은 '진행전' | 도넛은 사장님 실화면 컨펌 대기 상태라 라벨을 건드리지 않는다. **판정 함수만 공유** |
| 1000행 가드 | **넣는다** | 조용히 잘린 대장은 합계 푸터 숫자까지 틀리게 만든다 |

## 4. 설계

### 4.1 데이터 계층

`orders/page.tsx`의 select에 `공사이력!수주_id(count)`를 추가한다. DB가 수주별 이력 건수를
세서 붙여주므로 **쿼리는 여전히 1방**이고, 이력 행을 직접 받지 않으므로 1000행 캡은 수주
행에만 걸린다. 도넛이 쓰는 것과 같은 패턴(`TypeStatusDonutSection.tsx:18`).

- `수주행` 타입에 `이력건수: number` 추가
- `page.tsx`에서 `공사이력: [{count: n}]` 모양을 평평하게 풀어 `OrdersTable`에 넘긴다
- 조회 결과가 1000행 이상이면 **throw** (도넛 `TypeStatusDonutSection.tsx:27`과 동일 문구 체계)

### 4.2 공용 로직 추출 — 정본을 하나로

새 파일 `src/app/(dashboard)/_lib/연도.ts`:

- `연도`, `연도미상`, `연도선택`, `연도추출()`, `연도목록()` 을 `type-status.ts`에서 이동
- `type-status.ts`는 새 파일에서 import (기존 `type-status.test.ts`는 import 경로만 변경)

같은 자리에 상태 판정 함수를 둔다.

```
공사상태(준공여부: boolean, 이력건수: number): '완료' | '진행중' | '미진행'
```

도넛의 `공사행변환`이 인라인 삼항으로 하던 판정을 이 함수 호출로 교체한다. 수주대장도 같은
함수를 호출하되 **화면 라벨만 다르게 매핑**한다.

| 판정 함수 반환값 | 도넛 표기 | 수주대장 필터 표기 |
| --- | --- | --- |
| `'완료'` | 완료 | 준공완료 |
| `'진행중'` | 진행중 | 진행중 |
| `'미진행'` | 미진행 | 진행전 |

판정은 한 곳, 표기는 화면마다. 어휘를 통일하지 않는 대가로 이 매핑 표가 유일한 정본이 된다.

**왜 옮기나:** 이 함수들은 지금 도넛 전용 파일에 산다. 수주대장이 거기서 꺼내 쓰면 소유권이
애매해지고, 도넛을 고치는 사람이 수주대장이 매달려 있는 걸 모른다. 두 화면이 공통으로
기대는 규칙은 중립 자리에 둔다. 판정 규칙이 두 곳에 복사돼 있으면 한쪽만 고쳐질 수 있다 —
"세 화면이 같은 정의를 쓴다"를 코드로 강제하는 지점이 여기다.

### 4.3 필터 로직 = 순수 함수 + 테스트

현재 필터는 `useMemo` 안 인라인이다(`OrdersTable.tsx:163-178`). 조건이 3개에서 6개로
늘면 눈으로 검증이 안 된다. `orders/_lib/filters.ts`로 분리한다.

```
수주필터조건 = {
  연도: 연도선택                              // '전체' | number | '연도미상'
  상태: '전체' | '진행전' | '진행중' | '준공완료'
  원청사: '전체' | number | '없음'            // '없음' = 원청사_id null
  공사구분: '전체' | '총가' | '단가' | '민수'   // '민수'는 관급 포함
  검색어: string                              // 지중No · 공사명
}

수주필터(rows, 조건) → 수주행[]
원청사목록(rows) → { id, 거래처명 }[]         // 등장하는 것만, 거래처명 오름차순
연도선택목록(rows) → 연도선택[]               // '전체' → 최신연도 내림차순 → '연도미상' 맨 뒤
```

드롭다운에 건수는 표시하지 않는다 — 원청사 편중이 심해(정우전설 426, 나머지 대부분 1건)
숫자가 붙으면 선택을 돕기보다 잡음이 된다. 연도 선택지 순서는 도넛 `연도목록()`의 관례
(최신 위, 연도미상 맨 뒤)를 그대로 따르고 앞에 '전체'만 붙인다.

vitest로 못 박을 케이스 (레포 선례: `_lib/type-status.test.ts`):

- 관급 2건이 '민수' 필터에 걸린다 (회사 규정)
- 연도미상 1건이 '전체'에 포함된다 → **전체 건수 = 각 연도 건수의 합**이 항상 성립
- 원청사 없음 1건이 '없음' 선택지로만 잡히고 특정 원청사 선택 시에는 빠진다
- 상태 3분류가 서로 배타적이고 합이 전체와 같다 (완료 258 + 진행전 202 + 진행중 104 = 564)
- 검색어는 지중No·공사명 둘 다에 걸리고 대소문자를 무시한다 (기존 동작 보존)

### 4.4 UI — 필터 바 2줄

```
┌──────────────────────────────────────────────┐
│ [전체 ▾] │전체│진행전│진행중│준공완료│        │   ← 무엇을 조회할지
│ [원청사 검색 ▾]  [공사구분 ▾]                 │
├──────────────────────────────────────────────┤
│ │하도적용│공급가│  [🔍 지중No·공사명]  564건  │   ← 어떻게 볼지 + 검색
│                              [+ 새 수주]      │
└──────────────────────────────────────────────┘
```

- 상태는 4버튼 세그먼트 (기존 준공필터 스타일 그대로 확장)
- 연도 옵션은 **하드코딩하지 않고 데이터에서 파생** — 2027년 수주가 들어오면 자동으로 생긴다
- `SearchableSelect`를 `OrderForm.tsx`에서 `orders/_components/SearchableSelect.tsx`로
  추출해 폼과 필터가 공용한다
- 모든 필터 변경 시 `resetPage()` (기존 관례)
- 합계 푸터의 "/ 전체 N건" 표시는 지금 검색어에만 걸려 있다(`OrdersTable.tsx:473`) →
  **필터가 하나라도 걸렸을 때**로 조건을 넓힌다. 연도로 걸러도 "전체 몇 건 중"이 보여야 한다

### 4.5 폼 작업구분

`계약 정보` 섹션의 `공사구분·공사종류·공사현장` 3열에 하나 더 넣으면 셀렉트가 좁아져 값이
잘린다. **2열 × 2행**으로 바꾼다.

```
[공사구분]  [공사종류]
[공사현장]  [작업구분]   ← 신규
```

- 옵션: `['고압', '저압', '보수']`, 미입력 39건을 위해 `—`(null) 옵션 유지 — 기존 패턴
- 변경 지점 3곳: zod 스키마 · `defaultValues` · submit payload
- DB 컬럼·조회는 이미 존재 → **마이그레이션 없음**

## 5. 범위에서 제외

- 거래처 중복(`에스제이이` / `에스제이이2`) 정리 — 데이터 위생 별건
- `관급` 2건을 `민수`로 데이터 정정 — 코드 수정과 데이터 정정은 다른 작업. 필터가 병합
  처리하므로 조회에는 지장 없다
- 작업구분 필터
- 도넛의 '미진행' 라벨 변경
- 미입력 39건(작업구분)·1건(공사구분) 백필
